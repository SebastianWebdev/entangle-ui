# Entangle UI — v1.0 Stabilization Roadmap

> The final mile. After the `0.9.x` line closes (see `v0.9.x-roadmap.md`),
> the library has every planned component, an audited token system, perf
> + a11y baselines, and a Theme Builder. What it does **not** yet have
> is proof from real production use. This document covers that proof
> phase and the final stabilization release.

## Why a separate stage

Shipping `1.0.0` is a promise: the public API is stable, the defaults
make sense, the component coverage handles the cases real apps hit. The
only honest way to make that promise is to use the library in real apps
and fix what breaks. Synthetic stories in Storybook and example pages
in the docs site don't surface the same problems as a real product.

## Entry criteria

This roadmap activates when all five exit criteria on the `0.9.x` line
are met. If any of them slips, the work stays on the `0.9.x` line —
this stage does not start "in parallel".

## Phase A — Practical validation (user-driven)

The user builds 2–3 real applications on top of `entangle-ui@0.9.x` and
exercises the library against actual product requirements.

Target application profiles (representative, not prescriptive):

- A node-graph / pipeline editor (exercises NodeGraph, PropertyInspector,
  ContextMenu, FloatingPanel, Toolbar).
- A timeline / asset workflow tool (exercises Timeline, AssetBrowser,
  CommandPalette, Drawer, DataTable).
- An agent-UI / IDE-style app (exercises ChatPanel, FileTree, LogView,
  CommandPalette, PathBar, Tabs, SplitPane).

Goal of the phase: collect a real punch list of issues — missing props,
wrong defaults, awkward APIs, accidental coupling, performance cliffs,
a11y gaps, missing primitives. The agent's role here is reactive
(answering questions, fixing reported issues on the `0.9.x` line), not
proactive.

Output of the phase: an issue list in this repo, tagged for the
stabilization PR.

## Phase B — Stabilization PR

A single long-running PR against `main` that consolidates all the fixes
needed to ship `1.0.0`. Unlike the `0.9.x` line, this PR is **not**
patch-only — it carries the `major` changeset that lifts the library
from `0.9.x` to `1.0.0`.

Scope of the PR:

- Fixes for every issue raised in Phase A that the user accepts as
  in-scope for 1.0.
- API breaking changes (if any) — explicitly enumerated in the PR
  description, with migration notes for each.
- Final pass of changelog curation: the auto-generated `CHANGELOG.md`
  entries for the 1.0 release get a hand-edited summary at the top
  (highlights, breaking changes, migration guide link).
- One `major` changeset at the end (`"entangle-ui": major`) — this is
  the only place a `major` changeset is written in either roadmap.

Workflow:

- The PR stays open for the duration of Phase A's fix queue. Each fix
  lands as a commit on the PR branch, not a sub-PR (this is the one
  exception to the "small PRs" rule — we want the diff in one place so
  the final 1.0 release reviews as a single atomic change).
- The PR description maintains a live checklist of Phase A issues:
  open / fixed / explicitly deferred.

## What 1.0.0 means

When `1.0.0` ships, the following are committed:

- **Public API stability.** Component prop contracts, hook signatures,
  theme tokens, and `--etui-*` CSS variables are stable. Breaking
  changes require a major version bump and a deprecation window.
- **Reliability.** Components have been exercised in production
  applications, not just stories.
- **Default styling.** The default dark theme and the light theme look
  right out of the box; consumers shouldn't need to override tokens to
  get a coherent look.
- **Coverage.** Every component on the original flagship list ships, or
  has been explicitly deferred with a documented rationale.

## What 1.0.0 does **not** mean

- Not a feature freeze. Post-1.0 minor releases can add components.
- Not an exit from alpha-style iteration on parked items (high-contrast
  theme, RTL, mobile patterns, DatePicker) — these stay parked unless
  demand justifies the cost.
- Not formal WCAG certification. We hit the audit baselines from the
  `0.9.x` line; certification is a separate (paid) milestone if pursued.

## Post-1.0 hand-off

After `1.0.0` ships, planning for the next minor (`1.1.0`) starts from
the issues raised but explicitly deferred during Phase A, plus whatever
new demand has accumulated. That's a separate roadmap document, written
when we get there — not now.
